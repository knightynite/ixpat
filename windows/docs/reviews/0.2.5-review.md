# 0.2.5 review (independent review, 2026-10-24) and the triage

Read-only review of the two changes in 0.2.5: the crash handler (`win/crash_dump.*`) and the single-instance
guard with `--quit` (`app/main.cpp`). 10 findings; eight were fixed before the tag, two are recorded here with
the decision taken.

## Fixed

| # | Finding | Action |
|---|---|---|
| 1 | The filter wrote its line through the logger: a crash while the logger held its lock would deadlock, and the logger allocates | The fatal path appends its line with one Win32 call to a path prepared at startup; the logger is never touched after a fault |
| 2 | The dump was written on the crashing thread (nothing left after a stack overflow) and two threads failing at once shared the buffers | A dump thread waits from startup; the filter hands it the exception and waits; an interlocked gate lets the first fault through and parks the rest; a stack guarantee on the main and input threads |
| 3 | The setup (folder, retention) could throw before the handler was installed | Best effort inside a try; the directory walk uses error codes; the handler and the CRT hooks are installed whatever happened; the outcome is logged once |
| 5 | A mutex that could not be created at all let the app start unguarded | Logged, a message to the user, exit 1 |
| 6 | `--quit` returned once the window was gone; a slow teardown left the relaunch to wait, time out and exit 0 with nothing running | `--quit` waits for the window and then for the instance mutex (5 s each) and returns 1 when an instance remains; a launch that gives up returns 1 with a line in debug.log |
| 7 | Dump names had one-second resolution and `CREATE_ALWAYS` overwrote | The process id in the name, `CREATE_NEW`, a sequence number on a collision |
| 8 | The folder path was silently truncated into a fixed buffer | A path with no room for a dump name marks dumps unavailable, logged at startup |
| 10 | `--crash` matched any argument containing it; `--quit --crash` crashed the launcher | Whole tokens through `CommandLineToArgvW`; `--quit` wins; the self-test takes `--crash[=abort|throw|overflow|param]` |

Also from the review's notes: abort(), std::terminate, the CRT's invalid-parameter and pure-call exits route
through the same filter (each raises an exception with the thread's context first), and the debug CRT's dialogs
are off so a fault in a debug build dumps instead of waiting for a click.

## Known gaps (decided)

| # | Finding | Decision |
|---|---|---|
| 4 | A dump is process memory: it can hold the settings, the chord state and recent input reports, which the log policy (no key or text content) never allows in the logs | The dump type stays (the heap reachable from the stacks is what makes a dump worth reading). The design doc and the installed readme say what a dump can hold, that it stays on the PC and is never sent, and that attaching one to an issue is the user's choice |
| 9 | Retention ran on every launch, including `--quit` and a second launch, and reserved a slot by trimming to four | Trims to five at launch, so a crash can leave six until the next launch; a removal that fails is counted and logged |
| – | Fail-fast exits (the heap manager finding corruption, `__fastfail`, a stack cookie failure) end the process without visiting any in-process handler | Known; those need Windows Error Reporting's LocalDumps setting, which is a per-machine policy the app does not touch |
